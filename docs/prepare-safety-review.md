# 公開関数の準備：本番実行前の安全確認

本番実行には別途明示的な承認が必要。SQLはNOT_APPROVEDで停止する。

1. Supabase画面のプロジェクト名と参照IDを、運営者が保管する本番情報と目視照合する。SQLのテーブル構造による判定は接続先の証明にならない。
2. 読み取り専用preflightで最新のRLS・権限・公開件数を確認。既存の非公開データ、内部項目、秘密情報は画面外へ出さない。
3. 承認後の作業中は他のDB管理操作を止める。準備SQLは対象表をSHAREロックし、既存データ・ポリシー・テーブルACL・既存ロール所属・RLS状態を前後比較する。
4. 準備前にロール、関数3種、ポリシーの名前衝突を検出。既存内容と異なる場合は停止する。
5. 準備中に公開17・非公開1、公開関数17件と非公開除外、12項目、動画21項目の変換成功を検証する。件数は実行時に変わりうるため、相違時は停止し再確認する。
6. SQL Editorでエラーになった場合、同じ接続でROLLBACKし、別接続で残留を読み取り確認する。COMMIT後はROLLBACKで戻らない。権限を推測で変更せず、状態を監査する。
7. 関数が公開後に問題を示した場合は、別途承認された安全停止手順を検討する。この準備段階では原本SELECTがまだ開いている。遮断前に03-safe-stopを実行すると、原本SELECTも閉じて既存画面の閲覧に影響するため自動実行しない。
8. 原本SELECT遮断後の安全停止は、公開関数を停止して原本SELECTを閉じたままにする。旧フォールバック、匿名書き込み、公開バックアップは復活させない。閲覧停止が発生する。
