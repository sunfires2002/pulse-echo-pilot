## Safari調査

初回ゲートの旧keydown処理はEnterを無条件に保存に使用し、IME確定を区別していなかった。今回 composition 状態 / isComposing / keyCode 229 を判定する。これはコード上確認できる誤保存リスクであり、利用者のSafari入力不具合の原因を確定したものではない。

旧ダイアログは画面全体の固定配置に内部スクロール上限がなく、キーボードで可視領域が狭まった場合の余地が不足していた。名前ダイアログに限って高さを可視領域に合わせ、内部スクロール可能にした。縮小画面で保存に到達し、入力内容が残ることを検証したが、実ソフトキーボードの検証ではない。

実機で確認する項目: Safariでの入力欄タップ、日本語変換・確定、キーボード開閉、保存への到達、アドレスバー伸縮と拡大、キャンセル後の再入力。端末OS/ブラウザー版と具体的手順を記録する。

## 検証

`tests/common-profile.cjs` をChromeで実施。PC1440×900、Android相当393×851、iPhone相当390×844、小型320×568、横向き844×390、タブレット800×1024、Silk相当960×540。

全7条件: キャンセル、フォーカス復帰、IME確定中の保存抑止、350px以下の短い表示領域で保存操作と入力保持、保存名のホーム/試合間引き継ぎ、直接リンクの初回ゲート、スキップ、ゲスト名の後からの変更、送信者ID保持、変更後の名前で模擬投稿、コンソール例外なしを確認。Supabase HTTP/WebSocketは遮断・0件。

実Chart.jsを使用し、YouTubeとSupabase投稿はモック。実動画の再生・音声認識・実機キーボードの動作証明ではない。WebKitの実行ファイルがないためSafariエンジンは未検証。

既存 `tests/profile.cjs` も補助コピーで検証。旧グラフ高さの固定期待値3件を除外し、YouTubeモックを現行onReadyイベント/APIへ更新、実Chart.jsに置換した上で、名前/ゲスト/送信者ID/旧名移行/保存領域利用不可時/PC・TV・モバイル模擬投稿/Realtime表示がPASS。元のテストファイルは変更しない。
